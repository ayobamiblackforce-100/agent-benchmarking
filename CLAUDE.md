## Key learnings & principles
- **bash-terminal MCP tools only** reach the real machine; Claude's sandbox `create_file`/`str_replace` silently write to an isolated container instead — always verify a "file created" claim by reading it back via `bash-terminal:read_file` or `grep` over ssh/bash-terminal, especially right after switching tool families mid-conversation.
- **Sanity-check first-level results against an independent manual probe** before trusting a full concurrency/load-test sweep — tool/connector interruptions (MCP crash, laptop sleep) produce numbers that look superficially plausible (JSON parses fine) but are wall-clock garbage.
- **DB and agent-under-test don't need to be co-located** — `--db-dsn` on the concurrency harness works fine pointed at a different host than the agent, useful when the local machine can't run both.

### Added CPU/mem/GPU resource monitoring to the concurrency harness
- Tool used: bash-terminal MCP (run_command via `ssh root@162.243.213.185`, `scp`) for all remote work; python3 for local file patching (str_replace/create_file are sandboxed and don't touch the real filesystem — confirmed this repo is only reachable via bash-terminal); git for version control.

- Context: user asked whether CPU/GPU/mem utilization would be a relevant addition to the concurrency benchmark. It is — p95 latency alone can show "agent generation is the bottleneck" but can't distinguish a genuine hardware ceiling (GPU maxed out, need more capacity) from a serving-config ceiling (GPU idle, e.g. Ollama's default single-worker parallelism — fixable without new hardware).
- **Implemented**: resource sampling via `psutil` (CPU%, mem%) + `nvidia-smi` (GPU util%, GPU mem used) every 0.5s per concurrency level, background thread per level, results folded into `concurrency_summary.json/csv` and a new "Resource utilization by concurrency level" table in `concurrency_report.md`. Added `--no-resource-monitor` flag (on by default) to `run_concurrency_benchmark.sh`; `psutil` added to the venv install step.
- **Co-location guard**: sampling only runs when the agent-under-test is on `localhost` (checked via `_agent_is_localhost(AGENT_URL)`). If the agent URL points at a remote host, monitoring is auto-disabled with an explanatory note — sampling this host's CPU/GPU in that case would describe the wrong machine and silently mislead the report, rather than fail loudly.
- **Bug caught and fixed**: the file rewrite that added resource monitoring accidentally dropped the `POOL_MAX = max(CONCURRENCY_LEVELS) + 2` line (DB connection pool sizing), causing an immediate `NameError` on every run (`create_pool(..., max=POOL_MAX, ...)` with `POOL_MAX` undefined). Caught by actually running the smoke test rather than trusting `py_compile` (which passed fine — it's a runtime `NameError`, not a syntax error). Fixed by restoring the line near `CONCURRENCY_LEVELS`; verified with `py_compile` locally and remotely, then a clean re-run.
- **Validated end-to-end** with a small smoke run on the real H100 box (`162.243.213.185`, `qwen2.5-coder:32b`, Oracle DB co-located): levels 1,4, 2 rounds/level, 10 requests total. Resource sampling worked correctly — GPU util averaged ~20% at concurrency=1 and ~91% at concurrency=4 (genuinely GPU-bound, not host-CPU/mem-bound: CPU stayed under 13% max, mem under 3% throughout). Report's new findings section correctly interpreted this: "the GPU itself is genuinely near-saturated, so this is a real hardware capacity ceiling, not just a serving-config limit."

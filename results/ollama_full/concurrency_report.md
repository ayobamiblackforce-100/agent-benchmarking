## Findings

- Throughput scaled 2.01x from concurrency=1 (0.56 req/s) to concurrency=32 (1.128 req/s) - 32x concurrency increase would be linear/ideal, so scaling efficiency is ~6%.
- This is well below linear scaling (<50% efficiency), meaning the system is queueing/serializing work rather than handling requests truly in parallel.
- p95 agent generation time: 4.531s (concurrency=1) -> 34.735s (concurrency=32), 7.67x growth.
- p95 DB execution time: 0.684s (concurrency=1) -> 1.119s (concurrency=32), 1.64x growth.
- Agent generation time is both the larger share of total latency AND growing roughly in step with concurrency - classic sign of requests queueing behind a single (or too few) model-serving worker rather than running in parallel.
- GPU utilization at concurrency=32 averaged 82.3% (max 93.0%) - the GPU itself is genuinely near-saturated, so this is a real hardware capacity ceiling, not just a serving-config limit.
- Host CPU at concurrency=32: 10.6% avg, 84.6% max. Host memory: 3.6% avg, 5.0% max.
- No concurrency level showed an error rate above 5% - failures were not the bottleneck here.
- Correctness held steady under load: 0.4 at concurrency=1 vs 0.44 at concurrency=32 - correctness is not concurrency-sensitive here.

## Recommendations

- Agent/model serving is the primary bottleneck. If serving via Ollama, note it typically processes one generation at a time per model instance on a single GPU - consider deploying multiple backend replicas behind a load-balancing router (see ../multi-user-vLLM/docs/ROUTER.md in this workspace) so concurrent requests actually run in parallel across GPUs/instances instead of queueing on one.
- If serving via vLLM, check continuous-batching settings (e.g. max_num_seqs / max_num_batched_tokens) - vLLM can batch concurrent requests on one GPU far more efficiently than one-at-a-time serving, so a low ceiling there will look like this.
